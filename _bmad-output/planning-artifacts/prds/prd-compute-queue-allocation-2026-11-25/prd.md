# GPU 算力队列分配系统 PRD

## 1. 产品目标与使用者

实验室和课题组成员共享一台物理机的 GPU。系统让成员从 Web 页面提交训练或推理命令、查看排队及运行结果，并在资源满足时自动启动任务。资源管理员需要看到卡的占用情况、处理故障或维护，并在必要时终止任务。调度以先到先服务和单卡独占为基本承诺。同型号多卡任务可能让队首等待，即使此时有空闲卡，后续任务也继续排队。

本文依据 [SPEC](../../../specs/spec-gpu-queue-allocation/SPEC.md)、[架构文档](../../architecture/ARCHITECTURE-SPINE.md)、[源码](../../../../backend/app/main.py) 和 [测试与部署手册](../../../../docs/测试与部署手册.md) 整理。项目中的 CAP、Story 和测试用例编号继续使用。FR、NFR 编号为本文新增。

## 2. 版本范围与业务约束

**当前演示版**覆盖 Web 提交、严格 FCFS、同型号单组多卡分配、进程运行和回收、任务状态轮询、取消与终止，以及 GPU 管理 API 和只读面板。终止与多卡功能以 2026-10-29 的变更记录和当前源码为准。**后续范围**包括真实身份与角色、WebSocket、完整任务详情展示和 GPU 网页写操作，以及验收发现的可靠性缺口。计划项的交付批次仍待确认。 [Story 清单](../../../specs/spec-gpu-queue-allocation/stories.yaml) · [变更影响分析](../../../../docs/change_impact.md)

**验收范围**。课程演示检查提交、调度、运行与回收、状态查看、取消、终止和 GPU 管理的现有路径。多人部署建议以身份授权、资源一致性、MySQL 并发与实机设备映射通过为门槛，待 O-04 确认。

**术语**。FCFS 指先到先服务。**队首**是所有 `QUEUED` 任务按提交时间、任务 ID 升序排列后的第一项。**排队位置**是当前接口以 `QUEUED`、`PENDING`、`RUNNING` 合并计算的全局活跃序号，已运行任务也占序号。**分配记录**指每张卡各自的 `ALLOCATE` 或 `RELEASE` 记录。**终态**包括 `COMPLETED`、`FAILED`、`CANCELLED`、`TERMINATED`。

- **BC-01 单机资源池**。GPU、后端和调度进程位于同一物理机，目标使用单后端工作进程。本机直接部署，任务由后端运行账户启动本地子进程。Web 是成员操作入口，API 供前端和运维使用。
- **BC-02 单队列与整组分配**。全局 FCFS，按 `submitted_at ASC, id ASC`。优先级字段不参与排序。任务请求 1–64 张卡，实际满足量取决于登记且空闲的 GPU。同型号卡必须凑齐后整体分配，队首资源不足时暂停向后分配。
- **BC-03 卡的占用边界**。只有 `IDLE` 可分配。维护或故障卡退出资源池，恢复 `IDLE` 后重新参与调度。每张卡同一时刻只允许绑定一个任务。
- **BC-04 执行边界**。命令和依赖由提交方准备，后端传入所分配的 GPU。需要重定向等 shell 功能时，提交方显式调用目标平台的 shell。当前演示限可信用户及受控环境。组内多人试用须通过 FR-13 的身份和授权验收。
- **BC-05 MVP 范围外**。多节点集群、跨型号多卡、分型号独立队列、抢占和公平份额、预约和任务依赖、容器隔离、自动超时、完整认证套件与 SSO、外部通知、配额计费、GPU 硬件监控曲线、日志实时流和 CLI 提交。任务日志需可在运维侧定位。

## 3. 功能需求（FR）

**状态**。已实现表示当前源码可见。部分实现表示已有可用路径且目标能力仍有缺口。计划表示已有规格或 Story。拟补强表示依据风险记录形成的待确认需求。运行验收结果独立记录。

**优先级**。P0 为核心链路、安全或发布前置项，P1 为完整组内使用体验。[ASSUMPTION A1] 优先级是根据现有测试优先级、Story 和风险台账整理的建议，由 O-04 确认。

| --- | --- | --- | --- |
| FR-01 | 成员从概览页提交任务名称、命令、GPU 数量和可选型号。后端另支持可选的正数预估时长。Story 3-1、3-7 | P0 / 已实现 | 暂停分配后提交合法请求，返回 HTTP 201、任务 ID 和 `QUEUED` 状态，刷新后可查到记录。名称为空或超 128 字符、命令为空、卡数为 0 或 65 时，API 返回 422 且无新增任务。省略卡数按 1 处理，API 接受 64 作为请求值，实际可分配规模见 O-05。 |

### CAP-2 自动调度与执行

| 编号 | 需求 | 优先级 / 状态 | 验收条件 |
| --- | --- | --- | --- |
| FR-02 | 系统从全局队首开始分配空闲卡。单卡任务选数据库 ID 最小的空闲卡，当前单卡路径不按型号偏好过滤。Story 3-3 | P0 / 已实现 | 预置若干任务及足够 GPU，其中两任务提交时间相同。分配记录顺序符合时间及 ID 升序，已分配任务不会再获一组资源。无空闲卡时，队首保持 `QUEUED` 且无新增 `ALLOCATE`。对照 FCFS-01～04、GPU-01～03。 |
| FR-03 | 多卡任务整组获得同型号卡。用户指定登记型号时按该型号匹配，省略时取数据库 ID 最小的空闲卡的型号。Story 3-9、ADR-8 | P0 / 已实现 | 预置 ID 最小的空闲卡为 A 型，另有两张空闲 B 型。队首请求 2 张且指定 B 型时，一次分配两张 B 型卡，记录两个 GPU ID 和两条 `ALLOCATE`。省略偏好时队首等待，后面的单卡任务继续排队且该轮无分配记录。对照 MG-01～04、CHG-02～03。 |
| FR-04 | 分配后启动进程，跟踪执行结果并回收整组 GPU。Story 3-5 | P0 / 已实现 | 分配后任务为 `PENDING`、卡为 `ALLOCATED`。进程启动后任务及卡均为 `RUNNING`，任务记录开始时间。分别运行退出码为 0、非 0 以及无法启动的命令，任务分别为 `COMPLETED`、`FAILED`、`FAILED`，记录结束时间及退出结果，所有绑定卡恢复 `IDLE`、清空当前任务并逐卡写入 `RELEASE`。真实 GPU 映射按 NFR-06 验证。 |

### CAP-3 任务和资源可视化

| 编号 | 需求 | 优先级 / 状态 | 验收条件 |
| --- | --- | --- | --- |
| FR-05 | 查看任务状态、排队位置、关联 GPU 和运行结果，并区分成员与管理员视图。Story 3-2、3-8 | P0 / 部分实现 | **当前**。任务页轮询全量接口的首页（至多 100 条），显示状态、活跃任务的排队位置、GPU、提交时间及有起止时间时的运行时长。详情 API 返回起止时间与退出码，终态的排队位置为空。**目标**。以两个成员和一个管理员验证，成员在页面查询自己的任务详情，包括起止时间、退出码，管理员可查询全量记录。身份权限见 FR-13。 |

### CAP-4 取消与终止

| 编号 | 需求 | 优先级 / 状态 | 验收条件 |
| --- | --- | --- | --- |
| FR-07 | 取消尚在排队的任务。Story 3-6 | P0 / 部分实现 | `QUEUED` 任务取消后为 `CANCELLED`，有结束时间，释放队列位置，后续不再分配。当前对 `PENDING`、`RUNNING` 和终态取消返回 400。成员仅可取消自己的任务，鉴权见 FR-13。取消与分配的竞态按 NFR-05 验收，历史规格对 `PENDING` 的口径见 O-02。 |
| FR-08 | 管理员终止 `PENDING` 或 `RUNNING` 任务并回收资源。Story 3-6、CHG-01 | P0 / 部分实现 | **当前路径**。终止 `PENDING` 任务后不得启动任务进程。终止已运行的双卡任务后，确认该任务进程已退出、任务为 `TERMINATED`，两卡均可重新分配并各有一条 `RELEASE`。终止 `QUEUED` 或终态任务返回 400。当前失联路径可仅更新数据库，需单独核对进程存活。**目标补验**。终止与启动并发时，核对进程退出、任务终态和逐卡释放记录，重复请求不得再次释放。运行进程失联或终止超时仍存活时，禁止将其卡交给下一任务。管理员校验见 FR-13，平台要求见 NFR-06。 |

### CAP-5 GPU 资源管理

| 编号 | 需求 | 优先级 / 状态 | 验收条件 |
| --- | --- | --- | --- |
| FR-09 | 登记、查看和标记 GPU 资源。Story 2-3～2-5 | P0 / 已实现（API 与只读面板） | API 登记唯一名称、型号和正数显存后返回 201，初始为 `IDLE`。重复名称返回 409。列表及面板显示型号、显存、状态和当前任务，API 支持按状态过滤与分页。维护或故障卡不会被调度，恢复空闲后可以分配。`RUNNING` 卡直接标记 `MAINTENANCE` 或 `FAULTY` 返回 400。 |
| FR-10 | 管理员在 Web 面板登记 GPU、标记维护或故障、恢复可用和编辑备注。Story 2-5（登记入口沿用 2-3） | P1 / 计划 | 管理员从页面登记一张卡并在列表看到它，依次验证标记维护、恢复空闲、修改备注及刷新保留结果。对运行中 GPU 尝试标记维护时，页面提示拒绝且占用状态保持。普通成员无法提交 GPU 写操作。 |
| FR-11 | 保护调度器维护的 GPU 占用状态，覆盖管理写入与调度竞争。AR-05、R-04 | P0 / 拟补强 | 对已绑定任务的卡尝试通过管理 API 直接改为 `IDLE`，请求被拒绝且原绑定保持。让维护操作与分配并发执行，最终卡要么被维护且没有任务绑定，要么被任务占用且维护请求失败。无“空闲但绑定任务”的记录。 |

### CAP-6 并发分配安全

| 编号 | 需求 | 优先级 / 状态 | 验收条件 |
| --- | --- | --- | --- |
| FR-12 | 同一卡在任一时刻只分配给一个任务。分配同时保存任务状态、GPU 绑定和逐卡分配记录。Story 3-4、5-2、AD-1 | P0 / 部分实现 | 隔离 MySQL 中确认事务隔离级别为 `REPEATABLE READ`（由数据库配置决定），准备 1 张空闲卡和 100 个排队任务，并发触发 100 次分配且测试期间禁止释放。期望恰有 1 个任务获得卡、99 个仍待分配，卡的绑定与唯一 `ALLOCATE` 记录一致。分配过程中注入提交前异常，任务、卡及日志均无部分写入。源码已有行锁事务和并发测试。验收时须补齐 100 路场景对其余 99 个任务仍为 `QUEUED` 的显式断言。当前分配由后台执行。SPEC 的 99 个 HTTP 409 返回目标见 O-01。 |

## 4. 非功能需求（NFR）

性能目标沿用 SPEC。测量记录需注明服务器、数据库、GPU 数量、并发量和采样窗口。逐样本对照阈值，百分位及常态负载以 O-05 确认为准。

| 编号 | 质量目标 | 优先级 / 状态 | 验收条件 |
| --- | --- | --- | --- |
| NFR-01 | 提交确认 ≤ 200 ms（CAP-1） | P0 / 待测 | 从测试客户端发出合法提交到完整收到 HTTP 201 计时。记录原始耗时与失败数，对照 200 ms。 |
| NFR-02 | 可满足的队首任务在 GPU 释放后 ≤ 1 s 启动（CAP-2） | P0 / 待测 | 确认队首先前已排队、释放后资源足够且命令可启动。以 GPU 释放事务提交为起点，到队首任务 `RUNNING` 持久化为止。另记录分配及进程启动时间。 |
| NFR-03 | 排队任务取消 ≤ 100 ms 生效（CAP-4） | P0 / 待测 | 对排队中的任务从服务端收到取消请求到 `CANCELLED` 提交计时，复查随后无分配。运行中终止以进程退出及资源回收为准，关联 FR-08。 |
| NFR-04 | 已连接客户端在状态变更后 ≤ 500 ms 更新页面（CAP-3） | P1 / 计划 | 从状态事务提交到相关客户端页面显示新状态计时，并对照阈值。当前每 3 秒发起一次轮询，手动刷新或操作可触发额外刷新。 |
| NFR-05 | 竞态和重启后，资源占用、任务状态及记录一致（R-03、R-04、R-08） | P0 / 拟补强 | 并发触发取消与调度，仅允许取消成功且任务未获卡，或分配成功且取消被拒绝。分别模拟服务正常退出和异常中断，重启后仍活跃的任务保持正确占用，已停止的任务进入终态并释放卡，队列可以继续前进。当前取消路径未锁行，停止流程也缺少完整状态回写与重启对账。 |
| NFR-06 | 目标物理机的实际 GPU 可见性与任务分配一致（R-05） | P0 / 待实机验证 | 在有 NVIDIA GPU 的目标机逐一提交单卡和双卡 CUDA 探针。核查进程可见设备的 UUID 和数量、GPU 占用以及终止后无残留进程，结果与登记卡对应。Windows 验证进程树退出，Linux 按最终选定平台补验。源码当前直接写入数据库 GPU ID，SPEC 约定数据库 ID 减一的零基索引，验收以实际设备身份为准。 |
| NFR-07 | 对任务与 GPU 分配可追溯，系统异常可定位（Story 1-4、3-5、5-4） | P1 / 部分实现 | 以同一任务 ID 查询起止时间、退出码、任务输出及逐卡分配/释放记录。正常与异常退出均可追溯。模拟服务异常时，客户端收到通用错误，服务端日志保留诊断信息。`/health` 当前只表明后端可响应，部署验收另验证数据库读写和调度。 |

## 5. 成功信号与验收证据

- **SM-01 多人版提交到结果 ≤ 5 分钟**。按 SPEC 从成员登录开始，在测试卡短时占用期间提交预先准备好的 Python 脚本。先确认页面显示排队，随后释放测试卡，观察运行、完成和退出码，保留各状态时间。短任务的中间状态可由数据库或日志补证。依赖 FR-01、FR-04、FR-05、FR-13。
- **SM-02 100 路争用时重复分配数为 0**。按 FR-12 复核任务与资源绑定和分配日志。守护指标为越过队首和部分多卡分配次数均为 0，避免通过提前执行后续任务来改善等待时间。
- **验收记录**。将测试版本、环境、执行时间、输入、预期结果与实际结果对应到 FR 或 NFR，并保留相关 API 结果、页面、进程或数据库日志。SQLite 用于功能回归。并发锁测试使用专用、可丢弃的 MySQL 库，现有用例固定连接目标，且会执行建表与删表。正式执行前应完成专用库配置和库名保护，并停止连接同一测试库的后端。真实 GPU 映射及进程退出使用目标物理机复验。 [系统测试计划](../../../../docs/test_plan.md) · [风险台账](../../../../docs/risk_lisk.md)
- **现有成果**。演示材料展示 13 条 GPU 登记记录、任务 #7 绑定两张 RTX 4090、任务列表的终止入口和 GPU 只读表。历史日志摘要包含一次 Windows 执行的 `67 passed`，也有其他执行批次失败。上述证据用于描述现有成果，当前版本的计时、并发结果和真实 CUDA 映射仍待验收。 [概览](../../../../evidence/screenshots/01-overview-13-gpu-idle.png) · [双卡演示](../../../../evidence/screenshots/02-multigpu-running-2x4090.png) · [任务列表](../../../../evidence/screenshots/03-task-list-running-terminate.png) · [GPU 面板](../../../../evidence/screenshots/04-gpu-management-table.png) · [历史测试摘要](../../../../evidence/screenshots/test-logs/historical-results.md)

| O-04 | 确认计划项批次和优先级（A1），重点明确身份授权、WebSocket、GPU 网页写操作与重启恢复的上线门槛。 | 产品、开发、测试，排期及多人试用前。 |
| O-05 | SPEC 的 ≤ 8 张卡、≤ 20 个同时排队任务是原始规模假设，13 条页面记录是演示数据。确认基准环境、常态容量及延迟阈值的统计口径。`allocated_gpu_ids` 当前为 64 字符，无法记录 64 个逗号分隔的 ID。若交付范围要求 64 卡实配，需覆盖完整 ID 持久化与释放。 | 产品、部署、测试，性能验收前。 |
