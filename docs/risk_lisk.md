## 2. 风险明细

### R-01 并发 GPU 分配重复占用

- **场景**：多个 Dispatcher 实例或多个并发请求同时尝试分配同一张 IDLE GPU。
- **原因/依据**：分配依赖 Task/GPU 查询上的 `with_for_update()`；正确性依赖 MySQL 事务和行锁语义。
- **后果**：同一 GPU 被分配给多个任务、任务与 GPU 绑定冲突、资源统计不可信。
- **缓解措施**：
  1. 在隔离 MySQL 环境运行 `test_dispatcher_concurrency.py`。
  2. 验证 1 张 GPU + 50 个并发请求时仅 1 个任务成功。
  3. 验证 2 张 GPU + 30 个并发请求时仅 2 个任务成功。
  4. 验证 ALLOCATE 日志数量、GPU.current_task_id 和 Task 分配字段一致。
- **验收证据**：pytest 完整日志、测试库名、MySQL 版本和测试时间。

### R-02 并发测试可能清空错误数据库

- **场景**：开发者在未检查数据库连接的情况下运行 `test_dispatcher_concurrency.py`。
- **原因/依据**：该测试文件定义固定 MySQL URL，并在 autouse fixture 中执行 `Base.metadata.drop_all()`、`create_all()`，结束时再次 drop_all。
- **后果**：测试连接到开发或共享数据库时可能删除业务表。
- **缓解措施**：
  1. 不要直接在含真实数据的数据库执行。
  2. 创建独立数据库，例如 `gpu_queue_test`，并使用专用测试账号。
  3. 将连接地址改为环境变量注入，删除硬编码凭据。
  4. 测试启动时检查数据库名必须以 `_test` 结尾，否则立即失败。
  5. 运行前停止后端，防止后台 Dispatcher 同时写库。
- **验收证据**：脱敏后的连接配置、测试数据库名称、测试执行日志。

### R-03 服务停止或异常退出造成状态残留

- **场景**：后端正常关闭、进程崩溃或机器重启时，存在 RUNNING 任务。
- **原因/依据**：`ProcessManager.stop()` 会 kill 活动进程、清空 `_active_procs` 和 `_gpu_map`，但源码未在此处同步回写 Task/GPU 数据库状态。
- **后果**：任务仍显示 RUNNING，GPU 长期占用，队列无法继续使用资源。
- **缓解措施**：实现 graceful shutdown；在启动时执行 orphan reconciliation；保存 PID/进程标识并核验进程存活；对无法恢复的任务标记 FAILED/TERMINATED 并释放 GPU。
- **验收证据**：运行长任务后停止服务，再启动服务，确认任务状态、GPU 状态和日志一致。

### R-04 GPU 状态与任务绑定不一致

- **场景**：通过 GPU PATCH 接口直接修改 GPU 状态，或异常流程只更新一侧数据。
- **原因/依据**：GPU API 支持状态更新，当前主要限制是 RUNNING 状态不能直接改为 MAINTENANCE/FAULTY；未看到覆盖所有状态转换和 current_task_id 的统一规则。
- **后果**：GPU 显示 IDLE 但仍绑定任务，或 ALLOCATED/RUNNING 状态没有有效任务。
- **缓解措施**：将占用状态修改限制在 Dispatcher/ProcessManager；API 层建立状态转换矩阵；增加一致性巡检测试。
- **验收证据**：非法状态转换测试和一致性查询结果。

### R-05 CUDA_VISIBLE_DEVICES 使用 GPU 数据库主键

- **场景**：数据库中 GPU id 为 1、2，但物理机器 CUDA 设备索引或 UUID 并非 1、2。
- **原因/依据**：ProcessManager 将 `str(g.id)` 直接拼接为 `CUDA_VISIBLE_DEVICES`。
- **后果**：任务可能使用错误 GPU，或在设备不存在时启动失败。
- **缓解措施**：将数据库主键与设备索引分离，增加 device_index 或 GPU UUID 字段；登记设备时采集真实映射；部署验收时执行 `nvidia-smi` 与 CUDA 可见设备对照。
- **验收证据**：设备映射表、`nvidia-smi -L` 输出和实际任务环境变量。

### R-06 多卡 FCFS 队首阻塞

- **场景**：队首任务需要 2 张同型号 GPU，但当前只空闲 1 张；后续单卡任务即使可运行也不能越过队首。
- **原因/依据**：Dispatcher 明确在多卡资源不足时返回 False，保留队首阻塞语义。
- **后果**：GPU 可能空闲但任务不执行，资源利用率降低。
- **缓解措施**：在产品说明中明确此行为；监控队首等待时间；若未来采用跳过策略，需重新定义公平性并增加防饥饿测试。
- **验收证据**：多卡资源不足测试，确认队首和队尾均保持 QUEUED。

### R-07 缺少身份认证和授权

- **场景**：不同用户访问任务列表或调用终止接口。
- **原因/依据**：当前 API 默认 `user_id=1`，手册也将无认证列为 MVP 限制；终止接口未形成完整的管理员权限检查。
- **后果**：用户隔离、任务隐私和高权限操作保护不足。
- **缓解措施**：上线前增加认证机制、按用户过滤任务、管理员权限校验和审计。
- **验收证据**：不同角色的 401/403/数据隔离测试。

### R-08 终止任务时进程与数据库状态可能脱节

- **场景**：RUNNING 任务的 ProcessManager 内存映射中不存在对应进程，但操作系统进程仍存在；API 进入 DB-only fallback。
- **原因/依据**：路由在 ProcessManager 未发现活动进程时调用数据库终止回退逻辑。
- **后果**：数据库任务被标记 TERMINATED、GPU 被释放，但操作系统进程可能仍继续运行。
- **缓解措施**：持久化进程标识；DB-only fallback 前核验 PID/进程树；终止成功后再释放资源；增加异常重启和丢失内存映射测试。
- **验收证据**：终止后检查进程树、任务状态、GPU 状态和 RELEASE 日志。

### R-09 priority 字段未参与调度

- **场景**：用户提交不同 priority 的任务。
- **原因/依据**：Task 模型包含 priority，但 Dispatcher 排序仅按 submitted_at 和 id。
- **后果**：用户可能误以为高优先级任务会先执行。
- **缓解措施**：UI/API 明确当前不支持优先级；或后续定义 priority 与 FCFS 的组合规则。
- **验收证据**：需求说明和调度排序测试。

### R-10 SQLite 测试不等于 MySQL 并发验证

- **场景**：本地 SQLite 测试全部通过，就认为 MySQL 并发分配正确。
- **原因/依据**：项目常规 fixture 使用 SQLite；SQLite 不提供与 MySQL InnoDB 相同的行锁竞争语义。
- **后果**：并发缺陷可能在真实数据库出现。
- **缓解措施**：区分 SQLite 功能测试和 MySQL 并发集成测试；两类结果分别报告。
- **验收证据**：测试报告列出数据库类型、版本、测试范围。

### R-11 分配日志缺少数据库外键约束

- **场景**：任务或 GPU 被删除后，日志可能仍引用不存在的 ID。
- **原因/依据**：AllocationLog 的 task_id、gpu_id 字段当前为普通 Integer，模型中未声明 ForeignKey。
- **后果**：审计数据可能出现孤立引用。
- **缓解措施**：评估外键约束、软删除策略或定期完整性检查。
- **验收证据**：数据库 schema 和一致性巡检结果。

### R-12 前端轮询状态延迟

- **场景**：任务状态发生变化后，前端要等待下一轮轮询。
- **原因/依据**：项目手册说明前端使用 3 秒轮询，未实现 WebSocket。
- **后果**：状态显示不是实时，轮询规模扩大后请求数增加。
- **缓解措施**：MVP 阶段接受该限制；后续按任务数采用自适应轮询或事件推送。
- **验收证据**：手动操作与界面状态更新时间记录。

### R-13 测试依赖清单缺少 aiosqlite

- **场景**：在新 Windows 环境按 `backend/requirements.txt` 安装依赖后运行常规测试。
- **原因/依据**：`backend/tests/conftest.py` 使用 `sqlite+aiosqlite`，但项目 `backend/requirements.txt` 和根目录 `requirements.txt` 未声明 `aiosqlite`。
- **后果**：测试可能在创建 SQLite engine 时出现 `ModuleNotFoundError`，影响测试可复现性。
- **缓解措施**：将 `aiosqlite` 加入开发/测试依赖文件，或在测试依赖单独文件中声明；CI 安装测试依赖后再执行 pytest。
- **验收证据**：全新虚拟环境安装依赖后，常规 SQLite 测试可成功启动。
