# GPU Queue Allocation 系统 — 测试与部署手册

> 适用对象：测试人员 / 评审人员
> 适用范围：本项目（backend + frontend + MySQL 8 单机部署）
> 版本：v0.1.0（MVP，FastAPI + SQLAlchemy async + Vue 3 + Element Plus）

---

## 1. 系统简介

本系统是**实验室 GPU 算力排队与分配系统**。成员提交深度学习任务后，系统按 **FCFS（先到先服务）** 规则自动分配空闲 GPU，自动启动任务命令，并全程记录任务状态、GPU 占用与审计日志。前端提供任务提交、状态监控、队列查看、GPU 管理页面。

**核心流程**：用户提交任务 → 进入队列 QUEUED → 调度器分配空闲 GPU（PENDING）→ 自动启动子进程执行（RUNNING）→ 进程结束（COMPLETED / FAILED）→ GPU 自动释放回 IDLE。

**任务状态机**：`QUEUED → PENDING → RUNNING → COMPLETED / FAILED / CANCELLED`

## 2. 功能清单

| 模块 | 功能 | 说明 |
|---|---|---|
| 任务提交 | 填写任务名、执行命令、GPU 数量（1-N）提交 | 进入 FCFS 队列，返回排队位置；多卡任务限同型号组队 |
| 自动调度 | 空闲 GPU 自动分配 | Dispatcher 每 0.5 秒轮询，悲观锁保证并发安全 |
| 自动执行 | 任务命令自动启动 | ProcessManager 启动子进程，注入 `CUDA_VISIBLE_DEVICES`，日志写入 `backend/logs/{任务id}.log` |
| 任务查询 | 本人/全部任务列表、详情 | 含实时排队位置、运行时长 |
| 取消任务 | 仅可取消**排队中（QUEUED）**任务 | 从队列撤下，不启动 |
| 终止任务 | 可终止**运行中/启动中（RUNNING/PENDING）**任务 | 杀进程树（Windows taskkill /F /T）并释放 GPU，任务置 TERMINATED |
| GPU 管理 | 登记、查看、修改 GPU 状态 | 通过 API 操作；RUNNING 中的 GPU 禁止标记维护/故障 |
| 审计日志 | allocation_log 表 | 记录每一次 ALLOCATE / RELEASE |
| 前端面板 | 概览 / 任务队列 / GPU 管理 | 3 秒自动轮询刷新 |

## 4. 环境配置

### 4.1 MySQL 准备

1. 确保本机 MySQL 8.0 服务已启动（服务名 `MySQL80`，可用 `services.msc` 查看）。
2. 创建数据库（如不存在）：
   ```sql
   CREATE DATABASE IF NOT EXISTS gpu_queue DEFAULT CHARACTER SET utf8mb4;
   ```
3. 确认连接账号：当前配置使用 **root / 123456**（见 4.2，可自行修改）。

### 4.2 后端数据库连接配置（关键）

后端数据库连接串由 **`backend/.env` 文件**控制，**修改数据库只需改这一个文件**：

```ini
# backend/.env
database_url=mysql+aiomysql://root:123456@localhost:3306/gpu_queue
log_level=INFO
host=0.0.0.0
port=8000
```

- 连接串格式：`mysql+aiomysql://用户名:密码@主机:端口/数据库名`
- 换数据库/账号时，改这一行即可；**改完必须重启后端**。
- 若 `.env` 不存在，则回退到代码默认值 `backend/app/config.py` 中的 `mysql+aiomysql://root:root@localhost:3306/gpu_queue`。
- 也可用环境变量 `DATABASE_URL` 覆盖（优先级同 `.env`）。
- ⚠️ 后端必须在 `backend` 目录下启动，`.env` 才能被正确读取（相对路径）。

### 4.3 前端配置

前端 API 地址写死在 `frontend/src/App.vue` 顶部（`const API_BASE = 'http://localhost:8000'`）。后端换端口/主机时同步修改这里，改完刷新页面即可。

前端跨域已放行：`http://localhost:5173` / `http://127.0.0.1:5173`（见 `backend/app/utils/middleware.py`）。

### 4.4 首次依赖安装

```powershell
# 后端（虚拟环境已存在则跳过）
cd D:\working\compute-queue-allocation\backend
.venv\python.exe -m pip install -r requirements.txt

# 前端
cd D:\working\compute-queue-allocation\frontend
npm install
```

## 5. 启动系统

### 5.1 启动后端（重要：不要加 --reload）

```powershell
cd D:\working\compute-queue-allocation\backend
.venv\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

- 启动成功标志：日志出现 `Backend starting on 0.0.0.0:8000`、`Dispatcher started`、`ProcessManager started`。
- **⚠️ 严禁加 `--reload` 参数（Windows 平台）**：reload 子进程的事件循环不支持创建子进程，会导致所有任务命令启动失败、状态直接 FAILED（错误信息为空）。Linux 无此问题。

### 5.2 启动前端

```powershell
cd D:\working\compute-queue-allocation\frontend
npm run dev
```

浏览器访问 **http://localhost:5173**。

> 生产模式前端可 `npm run build` 后 `npm run preview`，或由 Nginx 托管 `frontend/dist`。

### 5.3 验证

- 后端健康检查：浏览器打开 `http://localhost:8000/health`，应返回 `{"status":"ok"}`。
- 接口文档（Swagger UI）：**http://localhost:8000/docs** —— 测试人员可在这里直接调用所有 API。
- 前端右上角显示 **Backend online** 绿色圆点即连通。

## 6. 数据库说明

### 6.1 四张数据表

| 表名 | 用途 | 关键字段 |
|---|---|---|
| `users` | 用户 | id, username, role(member/admin), gpu_usage_sec |
| `gpus` | GPU 资源 | id, name, model, total_memory_mb, status(IDLE/ALLOCATED/RUNNING/MAINTENANCE/FAULTY), current_task_id |
| `tasks` | 任务 | id, user_id, name, command, gpu_count, status, allocated_gpu_id, allocated_gpu_ids(逗号串，多卡), submitted_at, started_at, finished_at, exit_code, log_path |
| `allocation_log` | 分配审计 | id, task_id, gpu_id, action(ALLOCATE/RELEASE/TERMINATE/MAINTENANCE_*), notes |

### 6.2 初始化 / 重置数据库

```powershell
cd D:\working\compute-queue-allocation\backend
set PYTHONPATH=D:\working\compute-queue-allocation\backend
.venv\python.exe scripts\init_db.py --reset
```

- `--reset`：先删除全部表再重建（**清空所有数据**，谨慎使用）。
- 不带参数则只建表不删除。

### 6.3 查看 / 修改数据

推荐 DBeaver / Navicat / MySQL Workbench，连接：
- 主机 `localhost`，端口 `3306`，用户 `root`，密码 `123456`，数据库 `gpu_queue`。

常用排查 SQL：

```sql
-- 任务状态分布
SELECT status, COUNT(*) FROM tasks GROUP BY status;

-- 最近任务
SELECT id, name, command, status, allocated_gpu_id, started_at, finished_at, exit_code FROM tasks ORDER BY id DESC LIMIT 10;

-- GPU 现状
SELECT id, name, model, status, current_task_id FROM gpus;

-- 分配审计
SELECT id, task_id, gpu_id, action, notes FROM allocation_log ORDER BY id DESC LIMIT 20;
```

## 7. 页面操作指南

页面顶部导航含三个标签：**Overview**（概览）、**Tasks**（任务队列）、**GPUs**（GPU 管理）。所有页面每 3 秒自动刷新。

### 7.1 Overview（概览页）

**① 统计卡片（4 张）**
- Total GPUs：GPU 总数 + 空闲比例进度条（如 `50% · 1 / 2 idle`）
- Queued：排队中任务数
- Running：运行中任务数
- Completed / Failed：已完成 + 失败任务总数

**② 提交任务表单（Submit Task）**

| 字段 | 必填 | 格式要求 |
|---|---|---|
| Task Name | ✅ | 1~128 字符，任意文本 |
| Command | ✅ | **必须是系统可真实执行的命令**（见下方示例），否则任务会执行失败 |
| GPU Count | ❌ | 1 ~ 已登记 GPU 总数（多卡限同型号，上限 64）；多卡任务会**一次性**分配 N 张同型号空闲卡，凑不齐则保持排队 |
| GPU Preference | ❌ | 如 `RTX 3090`；**多卡任务的目标型号**（未填则以最早空闲卡的型号为基准）；单卡任务分配不按其过滤 |

Command 填写示例（Windows 下）：

```text
# 立即成功
cmd /c echo hello

# 运行约 60 秒（适合观察 RUNNING 状态和时长）
cmd /c ping -n 61 127.0.0.1 > nul

# 故意失败（验证 FAILED 分支与 GPU 回收）
cmd /c exit 1
```

时长换算：`ping -n N` ≈ **N-1 秒**。路径含反斜杠时请改用正斜杠（`D:/working/...`）。

**③ GPU 状态卡片**：每张卡的名称、型号、显存、状态（IDLE 绿 / ALLOCATED 橙 / RUNNING 蓝 / MAINTENANCE 灰 / FAULTY 红）、当前任务编号。

**④ Backend online / offline**：右上角指示后端连通状态；显示 offline 时所有功能不可用。

### 7.2 Tasks（任务队列页）

- 顶部标签栏实时统计各状态数量。
- 表格列：# / Name / Command / Status / Queue Pos / GPU / Submitted / Duration / Action。
- **Queue Pos**：排队位置（QUEUED/PENDING/RUNNING 中显示，其余显示 `-`）。
- **Duration**：运行时长 = `finished_at - started_at`（运行中显示 `-`）。
- **Cancel 按钮**：**仅 QUEUED 状态可点击**，用于把排队任务撤出队列；其他状态按钮为灰色不可点。
- **Terminate 按钮**：**RUNNING / PENDING 状态可点击**。点击后弹出确认框，确认后终止进程（Windows 下用 `taskkill /F /T` 杀整棵进程树）、释放 GPU，任务置 **TERMINATED**（终态，不可恢复）。

### 7.3 GPUs（GPU 管理页）

- 表格展示 GPU 的 # / Name / Model / Memory / Status / Current Task / Notes / Created。
- 当前页面为**只读展示**。添加 GPU、修改状态（如标记 MAINTENANCE）需通过 API 完成：

**添加 GPU（Swagger 或命令行）**
```powershell
curl -X POST http://localhost:8000/gpus -H "Content-Type: application/json" -d '{\"name\":\"gpu-3\",\"model\":\"RTX 4090\",\"total_memory_mb\":24576}'
```

**标记维护（PATCH /gpus/{id}）**
```powershell
curl -X PATCH http://localhost:8000/gpus/1 -H "Content-Type: application/json" -d '{\"status\":\"MAINTENANCE\"}'
```

> ⚠️ RUNNING 状态的 GPU 禁止直接标记 MAINTENANCE/FAULTY，会返回 400。

## 8. 测试场景清单（推荐执行顺序）

| 步骤 | 操作 | 预期结果 |
|---|---|---|
| 1 | 提交 `cmd /c echo hello` | COMPLETED，Duration≈1s，`backend/logs/{新id}.log` 内容为 `hello` |
| 2 | 提交 `cmd /c ping -n 61 127.0.0.1 > nul` | RUNNING 约 60 秒后 COMPLETED，Duration≈60s |
| 3 | 提交 `cmd /c exit 1` | FAILED（exit_code=1），GPU 自动回收为 IDLE |
| 4 | 提交 2 个长任务占满 GPU，再提交第 3 个任务 | 第 3 个任务 QUEUED（Queue Pos #1），其 Cancel 可点；点击后变 CANCELLED |
| 5 | 提交 3 个短任务，观察执行顺序 | 严格按提交时间顺序执行（FCFS） |
| 6 | 提交长任务，等它 RUNNING 后点 **Terminate** 并确认 | 任务变 TERMINATED、GPU 回 IDLE；再查 `tasklist | findstr ping` 确认后台进程已无残留 |
| 7 | 打开 `backend/logs/app.log` | 查看 Dispatcher/ProcessManager 完整调度日志 |
| 8 | 多卡测试：登记 2 张同型号 GPU（如 2×RTX 3090），提交 `gpu_count=2` 的短任务 | 任务一次性分配到 GPU #1、#2（表格 GPU 列显示 `#1 #2`，日志 `CUDA_VISIBLE_DEVICES=1,2`）；任务结束后两张卡**同时**回到 IDLE |
| 9 | 多卡自动化测试（SQLite，无需停后端） | `cd backend && .venv\python.exe -m pytest tests/test_multigpu.py -v`（15 个用例：多卡一次性分配、型号偏好、凑不齐队首阻塞、多卡结束批量释放、gpu_count 1-64 校验） |
| 10 | 并发测试 | `cd backend && .venv\python.exe -m pytest tests/test_dispatcher_concurrency.py -v`（**会清空数据库**，且需先停止后端） |

## 9. API 速查

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 健康检查 |
| POST | `/tasks` | 提交任务（body: name, command, gpu_count=1, gpu_model_preference 可选） |
| GET | `/tasks` | 当前用户任务列表（分页） |
| GET | `/tasks/admin` | 全部任务列表（分页） |
| GET | `/tasks/{id}` | 任务详情（含排队位置） |
| POST | `/tasks/{id}/cancel` | 取消 QUEUED 任务 |

| PATCH | `/gpus/{id}` | 修改 GPU 状态/备注 |

完整请求/响应示例见 Swagger UI：`http://localhost:8000/docs`。

## 10. 常见问题排查

| 现象 | 原因与处理 |
|---|---|
| 前端显示 Backend offline | 后端未启动 / 端口被占用。按 5.1 启动；检查 8000 端口监听 |
| 任务提交后立刻 FAILED、无运行时间、日志文件为空 | ① Command 不是真实可执行命令（如填了 `1`、`run`、`echo` 不带 `cmd /c`）；② 后端用 `--reload` 启动（Windows 必踩坑，去掉 --reload 重启） |
| 日志出现 `No module named 'app'` | 运行脚本前先 `cd backend` 并设置 `PYTHONPATH=backend` |
| 数据库连接报 1045 Access denied | `.env` 中账号/密码/库名错误；或不在 backend 目录启动导致读不到 `.env`（回退默认 root:root） |
| 修改 `.env` 不生效 | 修改后必须重启后端；确认工作目录为 backend |
| 前端提交表单校验报 Command is required | Command 字段未填，属于前端必填校验 |
| 初始化脚本尾部出现 `Event loop is closed` | aiomysql 退出清理的无害告警（已通过 `engine.dispose()` 修复），不影响建表结果 |
| 并发测试失败 | 需先停止后端实例，避免 Dispatcher 与测试同时操作同一数据库 |

## 11. 已知限制（MVP 范围，符合设计）

1. **无抢占/优先级**：队列严格 FCFS，`priority` 字段保留但不参与排序。
2. **GPU Preference 仅作为多卡任务的型号目标**：单卡任务分配不按其过滤；多卡任务以它为目标型号凑卡（未填则以最早空闲卡型号为基准）。按型号隔离独立队列仍未实现。
3. **终止功能已实现（2026-10-29）**：RUNNING/PENDING 任务可经 `POST /tasks/{id}/terminate` 终止（Windows 用 taskkill /F /T 杀进程树）；接口未做 admin 权限校验（随项目统一为 user_id=1 占位）。
4. **无 WebSocket 实时推送**：前端采用 3 秒轮询。
5. **无用户认证**：当前所有请求固定为 user_id=1（简化标识）。
6. **多卡限同型号（2026-10-29 新增）**：gpu_count 支持 1-N（上限 64），但必须同型号组队，不支持 4090+6000 跨型号混搭；凑不齐时队首阻塞等待（可能拖住后续单卡短任务）。
7. **Windows 开发限制**：后端不可用 `--reload` 启动（见 5.1）。
